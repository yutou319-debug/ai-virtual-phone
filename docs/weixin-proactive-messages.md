# 微信主动消息与分段输入合并

本改动在待发布分支中，不会自行部署或实际发送微信。

## 主动消息

沉默重连、追发、定时唤醒、已开启的经期关怀，以及此前的每日随机联系，均可沿用角色已扫码绑定且启用的微信 bot。

- 离线云端任务：绑定 bot 后固定使用微信发送已有生成结果，不要求模型输出“发到微信”标记。成功后沿用微信历史同步回 Float，不另写一份 outbox；失败时继续用原结果走 Float。
- Float 打开时生成的主动消息：正常保存后，只转发该批可见文字，不重新生成、不另写微信云历史，防止导入两份。普通聊天回复和群聊不自动转发；工具提示、状态/思维内容和图片/音频附件不作为正文转发。
- 转发失败或送达不确定：保留 Float 原消息，不自动重新生成或重发。网络中断、凭据过期等可能使微信收不到，但不会为微信多调用一次模型。
- 现有快捷动作本身可能有原来的续跑请求，本改动不新增这种请求。主动来电继续走原 Float 通话通知，不因固定微信通道变成普通文本。

这不是两个 App 必须同时弹窗的保证：离线微信发送成功时提示来自微信，Float 同步记录；前台 Float 的提醒仍遵循原设置。微信/系统通知权限、免打扰和专注模式仍可能影响弹窗。

## 微信分段输入

当前接入没有“用户收起输入框/键盘”事件；机器人自身的 typing 接口是向用户显示正在输入，不能读取用户键盘状态。

按用户选择采用 8 秒静默窗口：每次实际收到新消息重新计时，连续至少 8 秒没有新消息后，同一 bot 的待回复消息一起进入原有的一次生成流程。收集期间不调用模型。沿用现有生成锁，避免并行处理同一批；已回复的批次不重放。

8 秒是最低等待窗口，云端轮询、网络、模型耗时还会增加实际延迟；不是收起键盘后精确 8 秒回复。如果暂停发送超过窗口，即使仍在编辑未发送的文字，机器人也可能开始回复。开始生成后才收到的新消息属于下一批，不通过取消已付费请求重生成来强行合并。

接收时间在 getupdates 返回后记录，避免长轮询开始时间过早使窗口失效。使用服务器接收时间，不用用户设备时间；旧记录缺少接收字段时正常处理。

2. 更新个人 Supabase 离线推送函数，以及微信云助手（本次修改了 send-text 的转发模式）。只发布 Netlify 不足以更新云端逻辑。

无需每天打开 Float，但微信云助手、Supabase cron、模型配置和消息回复凭据仍须有效。仅扫码但没有部署云助手/同步运行包时，无法保证离线微信发送。

## 验证

`node scripts/check-proactive-weixin.cjs` 检查四种主动任务通道、安静时段、无 bot、前台正文转发与批次隔离、失败不重发及不重复写历史。

`node scripts/check-weixin-batching.cjs` 检查 8 秒窗口重置、三条消息合并成一次生成、并发轮询锁、已回复批次不重放、缺失待处理标志和设备时钟偏差。

另运行每日微信/每日规则、单次云回复、通话回归、微信提示词等价性（385 场景）和 TypeScript 检查。以上均为本地模拟；没有使用真实 API Key、发送真实微信或部署生产。

本版微信核心协议为 4。云函数拒绝加载旧协议 3 的桶内核心，改用已部署的新版内置核心；之后在 Float 同步运行包时会上传同版本核心。
